# Agentic DMS Step 6 — Supervised Runtime and Health Recovery

## Status

Step 6 converts the local DMS runtime from terminal-owned development
processes into a reboot-enabled systemd deployment. It does not change the
Step 5 authentication or tenant-authority model.

## Frappe process management

Frappe services are generated by the installed Bench version through:

```text
bench setup systemd --user <bench-user> --yes
```

Bench remains authoritative for the Gunicorn web process, Redis cache, Redis
queue, Socket.IO, scheduler, and RQ workers. The generated units are installed
under `/etc/systemd/system` and started through the Bench target.

Step 6 adds dependency drop-ins so MariaDB and Redis start before Gunicorn,
workers, the scheduler, and Socket.IO. The Bench target participates in the
top-level `dms-dashboard.target`, allowing a controlled restart of the complete
stack.

The local Node runtime is installed through NVM. A dedicated Socket.IO systemd
drop-in therefore supplies the absolute Node 20 binary directory and Bench
binary directory through `PATH`. This is required because systemd does not
inherit the interactive shell's NVM environment. The service continues to run
Bench's supported `bench socketio` command rather than bypassing Bench.

## Next.js process management

The frontend runs with `next start` as a dedicated systemd service. The service:

- requires the Frappe web service;
- uses the production `.next` build;
- restarts automatically after failure;
- uses the internal loopback Frappe URL for middleware session validation;
- exposes no password or API-key environment variables;
- sends output to journald.

`frontend/next.config.js` fixes the output tracing root to the frontend folder,
preventing unrelated parent lockfiles from changing the build root.

## Health and recovery

`scripts/dms_ops_healthcheck.py` validates:

1. the backend ping endpoint;
2. the frontend login page;
3. a real Engine.IO/Socket.IO opening handshake on port 9000;
4. Redis cache and queue connectivity;
5. MariaDB and installed-app connectivity through
   `dms.auth_setup.preflight_probe`;
6. all four local users and their exact DMS roles;
7. the required systemd units.

An enabled monotonic timer runs the first check 90 seconds after the supervised target starts and repeats five minutes after each completed check. Failure triggers a
rate-limited recovery service that restarts the complete
`dms-dashboard.target`, including Redis, Frappe web, Socket.IO, workers,
scheduler, and the Next.js frontend.

## Operator commands

From the repository:

```bash
./scripts/dms_ops_status.sh
./scripts/dms_ops_logs.sh
./scripts/dms_ops_restart.sh
```

System-level equivalents:

```bash
sudo systemctl status dms-dashboard.target
sudo systemctl restart dms-dashboard.target
sudo journalctl -u dms-dashboard-health.service
```

## Logging

Frappe's Bench-generated units continue to write under the Bench `logs`
directory. systemd may create those output files as root before dropping to the
service user, so logrotate runs the `copytruncate` rotation as root. The policy
keeps eight compressed weekly rotations and rotates early when a log exceeds
20 MiB. Next.js, health, and recovery logs are stored by journald.

## Boot behavior

`dms-dashboard.target` is enabled for `multi-user.target`. Within WSL, the
services start whenever the Linux distribution boots under systemd. Windows
must still start the WSL distribution; systemd cannot keep a stopped WSL VM
running.

## Security boundary

The supervised services bind to loopback ports `8000` and `3000`. This is a
local operations baseline, not an internet-facing deployment. A public reverse
proxy, TLS certificate, secure-cookie cutover, public domain, firewall rules,
and external monitoring require a known production domain and deployment host
and remain deferred.

Step 6 does not add write-capable agent tools or cross-resource joins.

## Baseline repair and rollback guarantees

The guarded installer does not assume that a previous best-effort rollback
restored every terminal-managed dependency. Before changing configuration or
installing units it snapshots the exact current state, then repairs and proves:

- MariaDB is running.
- Redis queue and Redis cache accept `PING`.
- The Frappe backend returns `pong`.
- The Next.js login route returns HTTP 200.

Redis processes are started from the Bench working directory so relative paths
inside the generated Redis configuration resolve correctly. Startup errors are
captured in the run report, and readiness is polled instead of being hidden
behind `|| true`.

The same bounded repair routine is used during rollback. A failed deployment
therefore reports whether the previous runtime was fully restored rather than
claiming success after merely launching processes.

## Operator restart behavior

`scripts/dms_ops_restart.sh` waits for every required systemd unit, the backend,
the frontend, and a real Engine.IO opening packet. It no longer relies on a
fixed sleep before reporting success.
